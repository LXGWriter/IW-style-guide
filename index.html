Instructional Writing Standards

I. Documentation Style Guide

This section details the standards for all public-facing company product literature. It includes general guidelines on overall style and standards that are particular to RealPage. The information in this chapter applies to all documents produced by the Instructional Writing Team.

Preface

The RealPage Documentation Style Guide is designed to assist the writers at RealPage®, Inc. by providing information about documentation standards.

RealPage standards closely follow the standards set forth in the Microsoft® Manual of Style. This document includes guidance and exceptions to the Microsoft Manual of Style. Style and Voice

An overview of style and voice are located in the Microsoft Writing Style Guide, formerly known as the Microsoft Manual of Style.

In general, the philosophy is to write in an upbeat, conversational tone. Write the way you'd speak to someone using the software if you were telling them how to do something. Be friendly but aim for brevity. Get to the point. Keep it simple.

Be Personal and Direct

When speaking of something the user should do, use you rather than the user, one, the operator, or some other indirect and impersonal reference.

For example, the phrases:

"The user must enter…"
"One must enter…"

is better written as

"You must enter..."
"Enter..."

"The user" is appropriate when writing about a third party in a process. For instance, when you explain user password setup, use "you" when describing the system administrator’s task and "the user" when describing the person whose password is being set up.

For example:

"Tell the user the password assigned by the system. The user can then sign on with that password."

Be Precise

Precision is crafting the language in a way that prevents readers from misinterpreting the meaning. Don't write to be understood. Instead, write so that you're not misunderstood.

For example:

"Windows allows two invalid passwords before it blocks the user."

Does this mean that Windows locks your computer after the second or third failed attempt?

Instead, write:

"After the third failed attempt, Windows locks your system."

In addition, using precise words like because rather than since, or using when/after rather than once can help. These are simply examples of finding and using terms the user is least likely to misunderstand.

Another method to ensure that your documentation is precise is to avoid vague or meaningless explanations and procedures.

For example:

"Make sure the  Accounting View option is active."

If the user doesn’t already know how to do this, the message doesn’t help.

Instead, write:

"In the Resident ledger, turn on the  Accounting View option."

Depending on the length of the procedure, it may be best to list the steps the user should follow. In some cases, it may be more appropriate to refer the user to a certain section in the training guide or add a link to the full procedure as a related topic.

UI Text vs. Grammar and Spelling

Make your documentation grammatically correct wherever possible. Occasionally, the text in the product interface (or even in an image of the product interface) is misspelled or uses incorrect grammar. In such cases, writers are to use correct spelling and grammar unless the change(s) will make it difficult for the user to identify what we are talking about.

One common example of an exception to this rule is the names of RealPage rights in user management. There are hundreds of rights in RealPage centers, many with similar names. To ensure that users will know exactly what right we are describing in our documentation, right names should always be documented exactly as they appear in the UI, regardless of errors in capitalization, grammar, or spelling.

For example, even if the UI shows a tab as, Leasing and rents, you should document it as the Leasing & Rents tab. (An ampersand is used because it is a part of the Leasing & Rents product name.) Or if the UI shows, Letters & Notices, you should document it as, Letters and Notices. (The ampersand is not included because Letters and Notices isn’t a proper name.)

Terms—Preferred Usage

The following list contains some preferred words:

  • Know the difference between type vs. enter (see MMS4, page 401).
    “Type” means to use a keyboard or keypad to place information into a UI element, such as a text box.
    “Enter” is an action, such as clicking the Save button, whereby you input information into the system.
  • Use words like “after” or “when” instead of “once”, per MMS4. Never use “once” in a temporal sense.
  • Use “because” instead of “since”, per MMS4.
  • Use ", and then" (comma and then) before the final action when more than one user action is performed in the same sentence.
    For example: "Click     Edit, type your information, and then click Close."

Terms—Technical

Avoid technical language unless there is a compelling reason why it is essential. Instead, use the most common language.

For example, use:

  • “Information” instead of “data” (if you must use data, use "data is" rather than "data are").
  • “Item” or “entry” instead of record.
  • “Send/receive” instead of upload/download. (This depends on context. When you refer to an email, “send/receive” is appropriate. When you refer to the Internet, upload/download is appropriate. Within the context of products such as SDE and Central Reporting, “import/export” is appropriate.)

Practical Issues of Style

Practical issues of style focus on the day‑to‑day writing decisions that shape clarity, consistency, and usability in instructional content. This includes choosing precise verbs, applying capitalization and punctuation consistently, using emphasis sparingly, handling terminology correctly, and aligning tone with user needs. Addressing these style considerations helps instructional writers reduce ambiguity and create content that is easy to follow and maintain. Consistent style choices support a shared voice across materials and reinforce a user‑centered approach to instruction.

In addition, the Microsoft Writing Style Guide provides a list of guidelines for writing in what they consider the "Microsoft style and voice." Their tips align with our general philosophy for good instructional writing.

Headings

Use title case for headings. In title case capitalization, also known as headline style, the first and last words (for example, The Text to Look For) and all nouns, pronouns (including its), adjectives (including this and that), verbs (including is), adverbs (including than and when), subordinating conjunctions (if, because, as, that, and so on), and prepositions over four letters are capitalized.

  • Capitalize the second word in compound words if it is a noun or proper adjective or the words have equal weight (for example, Cross-Reference).
  • Do not capitalize prepositions of four or fewer letters. However, regardless of size, do capitalize prepositions in phrasal verbs like move in or move-in.
    For example:
    "Using Rent Roll 2000 with Import Manager/Migrating from OneSite"
    "Completing the Resident’s Move-In Form/Backing Up Your Disk"
  • Articles (for example, a, an, the) are lowercase unless they are the first word in the title. Coordinating conjunctions (for example, and, but, or, for, nor), regardless of length, are lowercase unless they are the first or last word of the title or subtitle.
  • Whether to is used in infinitives or as a preposition, it is lowercase.
    For example:
    Preparing to Migrate Your Data (infinitive)
    Migrating from Rent Roll 2000 to OneSite (preposition)

For guidance on writing good headings, refer to Headings in the Microsoft Writing Style Guide. Just remember that our documentation standard instructs using title case for headings.

Product UI Elements

Title case is used for specific user interface (UI) elements to support readability, visual hierarchy, and consistency across the interface. These elements typically represent labels or text that function as identifiable UI components rather than instructional sentences. Applying the title case consistently helps users quickly recognize navigation elements, page-level identifiers, and named objects within the application. Instructional content should follow these conventions when referencing UI elements to align with the product interface and reduce cognitive friction for users.

As a general rule, use title case when referring to named elements of the client-facing product UI. Title case is used for page names, modal (or box) names, page section names, list names, list column names, and field names.

Here are examples of user interface elements where you use title case:

  • Use title case when referring to a product center name.
    For example: "If the Document Management product center is active in your property, then the     Documents tab is available in applicant and resident accounts."
  • Use title case when referring to a report title. (Also use italic font.)
    For example: "You should run the     Monthly Transaction Summary report as part of your month-end close process."
  • Use title case when referring to a column in a report. (Also use bold font.)
    For example: "The     Net Prepaid amount on the Delinquent and Prepaid report should match the Prepaid Portion amount on the Resident Summary Balances report."
  • Use title case when referring to a user management role.
    For example: "People who are assigned the role of Property Manager, Regional Property Manager, or Superuser automatically have this right."

Titles

The following rules are for references within a sentence.

  • Report Title: Use title case, italic. Do not include "report" as part of the title, even if the name of the report in the user interface includes "report."
    For example: "The     Certifications report lists the certifications in effect during the report period that you define."
  • Book Title: Use title case, italic.
    For example: "See the     Document Management Training Guide for more information."
  • Chapter Title: Use title case, bold.
    For example: "See Chapter 6,     Formatting, to learn about bulleted lists."
  • Person’s Title: Capitalize the title before a person’s name, but don’t capitalize the title after or apart from the person’s name.
    For example: "Regional Manager Jane Doe ran the month-end procedures. The related documents were later printed by the regional manager."

Trademarks

Use ®, ™, and © where appropriate.

  • Cover or Title Page: The ™ and ® symbols are used on the first use of a trademarked or registered trademarked product or item on the cover or title page. For all training guides, the symbols are included in the product logos and do not have to be manually added to the covers.
  • First Use: The ™ and ® symbols always follow the first use of a trademarked or registered trademarked product or item in the body of the document. As with all product documentation, "first use" is difficult to define.
  • Headings: If the first mention of a trademarked product occurs in a heading, then it is not necessary to use the trademark symbol, provided that the trademarked product is mentioned immediately in the text that follows the heading.
  • Copyright: Only the copyright symbol ©, not the word "Copyright," is required in copyright notices. Including the word "Copyright" does not afford any protection in addition to the symbol alone and is therefore unnecessary.

For all training guides, copyrighting is standardized to the copyright page only.

URL

Use all lowercase for a Uniform Resource Locator (URL).

For example: "Go to www.realpage.com and click the Services tab."

Care should be taken when working with URLs, especially if they are long. The URL should never break over lines or wrap through two lines. Instead, rewrite your sentence so that the URL is set off in a separate paragraph.

For example: "To enter a request, go to the following website and click the Support request button: https://property.onesite.realpage.com/crossfire/availability/”

Emphasizing a Prohibition

Use emphasis sparingly. Apply the Emphasis style in Author-it to any word that needs to be highlighted in the text. The Emphasis style automatically italicizes the selected word.

Do not use all caps to emphasize words.

For example: "Do not continue without a backup."

Grammar

In instructional writing, consistent application of standard grammar rules reduce ambiguity. It ensures that readers interpret instructions as intended. Effective instructional grammar emphasizes clear sentence structure, correct verb tense and voice, proper agreement, and accurate punctuation.

Generally, instructional writers follow the Grammar and Parts of Speech Checklist in the Microsoft Writing Style Guide. Some examples are listed in this section.

Active vs. Passive Voice

 A verb’s voice tells whether the subject of the sentence performs the action (active) or is acted upon (passive). Use an active voice whenever possible. It is almost always clearer, more concise, and provides more relevant information than passive voice.

In general, the best rule of thumb is to be direct. When speaking of something the user should do, use you rather than the user, one, the operator, or some other indirect and impersonal reference.

Two examples of being direct:

  • "You must enter..."
  • "Enter..."

"The user" is appropriate when referring to a third party in a process. For instance, when you explain user password setup, use "you" when describing the system administrator’s task and "the user" when describing the person whose password is being set up.

Use passive voice only when you need to keep continuity with the subject of the paragraph, when the subject is too complex to state, or when the subject is unknown or is less important. However, never use passive voice to cover for a lack of important knowledge about the subject. Often, further research is the remedy for a sentence that uses passive voice.

Collective Nouns

A collective noun is a non-plural form of a noun that refers to a group of people or objects, like "group" or "staff." Collective nouns take singular or plural pronouns and verb forms depending on their meaning.

Use a singular pronoun and/or verb form with a collective noun when referring to the group as a unit.

For example: "If the property staff has completed all date-sensitive tasks scheduled for the day, you will be able to forward the property date."

When referring to the individual members of the group, use a plural pronoun and/or verb form.

For example: "Property staff use the "My tasks" option to manage their individual task assignments."

Make Prohibitions Direct; Include Positive Direction

Strive to make prohibitions direct and include positive direction along with the prohibition.

For example: "While HUD encourages the use of special characters (@, #, $, and so on) in the password, RealPage does not encourage this."

This prohibition is weak—it tells the users we don’t encourage this action but doesn’t tell them not to do it directly. The instruction is also weak because it provides no positive direction.

This should be: "While HUD encourages the use of special characters (@, #, $, and so on) in the password, do not use them because they sometimes cause errors. Only use letters and numbers in your password."

This instruction clearly tells the user what not to do and what should be done.

File Types and Extensions

File types are names given to specific kinds of files. File types often use the same letters of a file extension. For example, DOC indicates a Microsoft Word document, and ZIP indicates a compressed, or zipped, file.

File extensions are used at the end of a file name and indicate the format of the file. Use a leading period and the file extension when referring to specific file names.

The following examples show how file names and extensions should be written:

  • "WeeklyMeetingNotes.doc"
  • "UserGuideUpdates.zip."

Here are some examples demonstrating how file names are written in speech:

  • "Drag the floorplan.xls file to the directory."
  • "Click the brokenmirror.jpg file to open it."

When referring to specific file types, use all caps as seen below:

  • "You can print the PDF file."
  • "Supported file types are JPEG, MOV, MP4, GIF, XLS, and PDF."

Split Infinitives

A split infinitive occurs when an adverb or adverbial phrase is placed between "to" and the verb. While prohibited in formal English, split infinitives may be acceptable in the interest of writing in a conversational tone.

Example 1: “You should instruct users to not change their assigned passwords."

This would sound less awkward if we do not split the infinitive:
"You should instruct users not to change their assigned passwords."

Example 2: "You can set up the system not to include former residents in this list."

This would sound less awkward if we do split the infinitive:
"You can set up the system to not include former residents in this list."

Split Verb Phrases

The English language permits phrasal verbs to be split. For example, you could write either "set up the interface" or "set the interface up." When there are three (or fewer) words between the two parts of the verb (in this example, between "set" and "up"), either construction is acceptable. The split construction sometimes sounds more natural when using a conversational style. However, if there are four or more words between the parts of the verb, strive to keep the verb together.

For example: "If you have set any new recurring transactions up…"

This would sound less awkward as: "If you have set up any new recurring transactions…"

The next example is specific to the use of the word 'only.'

Correct Usage: "This Action is available only if you are authorized to override screening decisions in user management."

Incorrect Usage: "This Action is only available if you are authorized to override screening decisions in user management."

The verb phrase in this example is "is available" while the condition is the prepositional phrase/object "if you are authorized…"

Punctuation

Punctuation usage is covered in the Microsoft Writing Style Guide. Aside from these exceptions, our general rule is to follow Microsoft's guidelines for Punctuation. This section discusses frequently encountered situations involving punctuations.

Colons

Use a colon to introduce a concluding explanation, series, appositive, or long or formal quotation. (An appositive is a noun or noun substitute that renames another noun immediately before it—for example, my property manager, Bob.)

As an introducer, a colon is always preceded by a complete main clause (a word group that contains a subject and a verb and does not begin with a subordinating word). It may or may not be followed by a main clause. This is one way the colon differs from the semicolon, which generally separates main clauses only.

For example: "A packet is similar to a file folder: it is an electronic collection of documents that define and enforce your processes."

Sometimes a concluding explanation is preceded by the following or as follows and a colon.

For example: "A more precise definition might be the following: a packet is a mechanism that defines the documents required to fulfill your operational policies, collect those documents electronically, and ensure that company policy is enforced."

You can use a colon to introduce a series. Whether the items in the following series are separated by commas or semicolons depends on whether the items are short (such as noun phrases) or lengthy (such as complex phrases or clauses).

For example: "There are three electronic filing cabinets: Leasing, Property, and Vendor."

Use a colon after the salutation of a business letter, between a title and subtitle, and between divisions of time.

Capitalization

Do not capitalize the word following a colon unless the word is a proper noun or the text following the colon consists of more than one sentence. The exception to this rule is the Bulleted List Labels, below.

For example: "This option is only available if you are using one of the following: Leasing & Rents or Leasing & Rents—Affordable (HUD)."

For example: "There are two steps in the process: First, define your packets at RealPage Central. Second, push the packets to each property that will use them."

Bulleted List Labels

Colons are often used at the end of a lead-in statement that presents a bulleted list. In this case, the colon normally follows a noun or a short phrase.


For example:                                                                                                                       

Select the value you want to use to locate the property you are looking for:

  • City: Select this option to list properties in a particular city.
  • Property name: Select this option to find properties based on their property name.
  • Site ID: Select this option to find properties based on their OneSite identification. This is a number that is unique for every property in OneSite.
  • State: Select this option to find properties in a specific state. Enter the two-letter state abbreviation.
  • ZIP: Select this option to find properties in a specific ZIP Code area.

When a colon follows a word in bold, then make the colon bold. Use one space following the colon. The definition after the colon should begin with a capital letter.

 

Commas

Use a comma between main clauses that are joined by a coordinating conjunction (and, but, or, nor, and sometimes yet, so, and for).

For example: "Click the Save button and the system updates the list with your changes."

Instead, write: "Click the Save button, and the system updates the list with your changes."

Use a comma to set off introductory phrases and clauses.

For example: "By adding these details to service requests Facilities reports help manage costs."

This should be: "By adding these details to service requests, Facilities reports help manage costs."

Ellipses

The ellipsis mark (…) indicates a break in continuity. In general, avoid using an ellipsis unless it is not otherwise clear that you have left out material from the source.

For example: "But all these places…are so different…."

There are four dots at the end because of the sentence period and the three-dot ellipsis mark.

In general, it is rare to use ellipses because we don't usually leave out material from the source. However, there are cases when this may be appropriate. Some OneSite pages have "field" names that are long sentences or questions. In these cases, you can properly use the ellipses almost as an abbreviation.

For example, a OneSite field has the following name: "Does the Household Qualify for an Elderly Deduction?"

For simplicity, you can document this field name to: "Does the Household Qualify..."

The rule is whether the full name or the elided name makes the sentence clearer. In practice you can describe long field names in training guides as seen below:

"Does the Household Qualify...: The default time to make prospects/traffic inactive is 90 days after the last follow-up activity (based on the property date and the last follow-up date). Accept the default or enter a new number of days."

Hyphens

The Punctuation section of the online Microsoft Writing Style Guide includes guidelines on how to use dashes and hyphens. The following guidelines and examples are provided as guidelines for common issues and RealPage specific examples.

Hyphens are used to separate double vowels occurring with prefixes. Use a hyphen in certain instances where prefixes are added to words and a confusing double vowel occurs. This is especially needed when the added prefix might give the impression of a diphthong. However, in Leasing & Rents—Affordable documentation, we follow the HUD convention of using "reexamination."

For example:

pre-examination

anti-immigration

Annual Reexamination

Hyphens vs. Dashes

Make sure you use a true hyphen (-) to hyphenate a word. Use the em dash—shown here—to separate a part of the sentence. Parentheses are often preferable to the em dash, but you should use the em dash to set off a phrase that deserves more emphasis.

Hyphen

The following list shows the various uses of the hyphen:

  • Use a hyphen in certain compound nouns (for example, great-grandmother).
  • Use a hyphen in a fraction or compound number (for example, one-half, sixty-six).
  • Use a hyphen in a compound adjective (for example, up-to-date report or check-writing history).
Em Dash

Use the em dash sparingly, and then only for deliberate effect. The following list shows the various uses of the em dash (no spaces):

  • To show a sudden change of thought. (Because the actions list is dynamic—it changes according to the lease status—actions are listed here by lease status.)
  • Before a summary of what is stated in the sentence.
  • To show emphasis. (The Conventional options are available for all Affordable properties—layered or not.)
En Dash

The en dash is half the length of an em dash. Use the en dash in certain headings. Insert space before and after it.

For example:
"Knowledge Review – Adding a Prospect"

You can also use the en dash in page names or to separate parts of page names.

For example:
"The Manage model – Properties page opens."
"The Central setup – Edit Excel template box opens."

We also use the en dash in certain status codes. In these cases, there are no spaces before or after the en dash.

For example:
"Invoices that are Open or Open–Partial are eligible for export."

The en dash means "up to and including" in expressions. There are no spaces before or after the en dash in these cases.

For example:
"Open 10 A.M.–6 P.M., Monday–Friday"
"During the years 1999–2006"
"The training class scheduled for July–August 2006"

You may use the hyphen, the em dash, and the en dash in the same sentence, but you should avoid doing this because it is likely to distract the reader from his or her task.

Do not use the hyphen, em dash, or the en dash following a bulleted list label. Instead, use the colon.

For example:
"Delete—To remove an item from the list of available items, click this link."

Instead, write:
"Delete: To remove an item from the list of available items, click this link."

Possessives

Do not form possessives from company names. Do not use possessive forms of product or feature names.

For example:

  • "It is RealPage’s policy to…"
  • "Many of OneSite’s reports are…"

Instead, write:

  • "It is the policy at RealPage to…"
  • "Many OneSite reports are…"

For example:

  • "Windows’s interface"
  • "Word’s templates"
  • "the spell checker’s dictionary"

Instead, write:

  • "the Windows interface"
  • "Word templates"
  • "the dictionary in the spell checker"

Quotation Marks

Use single quotation marks to enclose a quotation within a quotation.

For example: "Asset is under warranty 'as is' unless another agreement is settled upon."

When using technical terms, business jargon, or coined words or phrases not likely to be familiar to our readers, you may enclose those in quotation marks when they are first used.

Quotation marks may enclose words being used in a special sense. It is not necessary to continue using the quotation marks beyond the first usage.

For example: There are several "must pass" criteria.

Periods and commas always go inside closing quotation marks. The placement of other punctuation marks depends on whether the punctuation is part of the quote.

For example: The message should read, "Process Complete."

In typed values, use quotation marks to identify values that the user types into a data entry field. This is commonly used when providing an example to illustrate a system function.

For example: If you enter "John and Mary Smith" as the household name, this value will be used in the final account statement instead of the head of household's name.

Semicolons

If you are using a semicolon, then consider rewriting with a simpler sentence structure.

As a general rule, avoid semicolons in user documentation. Semicolons are often misused in certain constructions that call for other punctuation or no punctuation. Even when used correctly, too many semicolons can make writing choppy. In most cases, the sentence can and should be written as two sentences.

For example: "Use this option to define the frequency of the job; for example, to run the report every Monday, select 'Recurring' and 'Monday.'"

Rewrite this as: "Use this option to define the frequency of the job. For example, to run the report every Monday, select 'Recurring' and 'Monday.'"

Spacing After Punctuation

Use one space after ending punctuation (periods, question marks, and exclamation points). Also, use one space after a colon.

For example: "There are two steps in the process: First, define your packets at RealPage Central. Second, push the packets to each property that will use them."

When using an en dash as part of a heading, use spaces around the dash.

For example: "Make a Decision – Applicant Approved with Conditions"

When using an em dash to separate a part of a sentence, do not use spaces around the dash.

For example: "The Conventional options are available for all Affordable properties—layered or not."

Acronyms and Other Abbreviations

Usage of acronyms and abbreviations is covered in the Microsoft Writing Style Guide. Bulleted Lists

Use a bulleted list for an unordered series of concepts, items, or options or as substeps to numbered procedural steps. Use a single bullet for a single step procedure.

Unordered Lists

Capitalize the first word of each bulleted entry. Use a lead in, normally a noun, a short phrase, or even an entire sentence, before the unordered lists. Use the colon to follow the lead-in text; do not use the hyphen, en dash, or em dash.

End each entry in a list with a period if all entries are complete sentences, are a mixture of fragments and sentences, or complete the introductory sentence.

Bulleted entries that start with a field name or a button name followed by a colon should be in title case/bold. When a colon follows a word in bold, bold the colon. Use one space following the colon.

All items in the list should be either complete sentences or fragments. All items should begin with either a noun or an imperative verb. All descriptions should be descriptive rather than a command. This is also a consistency issue.

Example of an unordered list:

Select the value you want to use to locate the property you are looking for:

·       City: Select this option to list properties in a particular city.

·       Property Name: Select this option to find properties based on their property name.

·       Site ID: Select this option to find properties based on their OneSite site ID. This is a number that is unique for every property in OneSite.

·       State: Select this option to find properties in a specific state. Enter the two-letter state abbreviation.

·       ZIP: Select this option to find properties in a specific ZIP Code area.

 

Do not use a single bullet in a list. Generally, the information can be merged with the preceding paragraph, made a "regular" paragraph by itself, or merged with the information that follows.

The only exception to this rule is if there is a single step to a procedure. Then use a bullet instead of a number to list out the step.

Numbered Lists

Use numbered lists in a procedure to take users through a specific sequence of events. Use the List Number paragraph style to create the numbered lists. Only actions taken by the user should be numbered steps, not system responses. Capitalize the first word of each entry.

Example:

To view the amenities for a unit:

1. Click the Unit (number) link of the unit to access the View Details pane.

2. Click Amenities tab to list the unit's amenities by name, category, type, and value.

3. Click Close to return to the Unit Availability page.

Use alpha lists exclusively for callouts and not as a substitute or a subset of numbered (procedural) or bulleted (unordered) lists. (See Callout Graphics for more information.) This standard is particularly helpful when you insert a labeled callout in a numbered procedure, as it lets you clearly distinguish between the procedural steps and the callout items.

Procedure Standards

The procedure topic typically provides instruction on how to perform specific tasks. You can have a single process or several related processes in a procedure topic. The format of the information in this topic varies depending on the simplicity or complexity of the procedure. Use the following procedure standards.

Titles
  • Singular or Plural
  • Finding Residents
  • Finding a Resident
Content

Use the following guidelines to create the content for your procedures:

  • The title of the procedure should identify the main function of the tasks that it describes. Use the gerund form of the verb. You can use singular or plural nouns, depending on the type of task.
  • Example 1: Singular Procedure Title
    “Canceling a Move-Out Notice”
  • Example 2: Plural Procedure Title
    “Managing Balance Payments”
  • Optionally, provide an introduction to the content of the procedure. For example, if the procedure topic provides several related processes, you can use an introduction to explain how these topics relate.
  • Precede the steps with an introductory phrase, such as "To add an account".
  • Use numbered steps to document the process.
  • Your first step should describe how you open the page, pane, tab, step, or task from the parent page that you listed in the path. You might need more than one step.
  • Use imperative verb forms and consistent sentence structures.
  • Avoid steps that don't have actions.
  • Apply either a List Continue or Note style to informational items that contribute to or are the result of the process but are not steps.
  • Place informational items that do not contribute to the process in the relevant Fields topic entry.
  • Include only the information that the user needs to complete the step or process.
  • Include images only when they are necessary to add clarity to a step. For example, if a field is difficult to locate or the result of the step is difficult to explain in words.
  • Avoid using several sentences in a step. Use a single sentence step with or without a result.
  • Example 1: Step without Result
    “Type the applicant's name in the Name field.”

  • Example 2: Step with Result:
    “Use the     Status drop-down list to select the applicant's status. The list updates to include only applicants with the selected status.”
  • Define the options in a drop-down list when the meaning of one or more of the options is not clear OR the choice significantly affects the outcome of the procedure. For example, you don't need to explain move out reasons, but you do need to explain specific chart or report types.
  • Example 1: Drop-Down List without Options
    Use the     Status drop-down list to select the applicant's status. The list updates to include only applicants with the selected status.
  • Example 2: Drop-Down List with Options
    Use the     Chart Type drop-down list to select the chart type you want to view.
  • Item Count: This chart shows the number and percentage of rentable items at the property by unit status.
  • Market Value: This chart shows the market value amount and percentage of rentable items at the property by unit status.
  • Provide a step to finalize the process, such as saving the entered information or clicking close to return users to their original page.

III. Graphics Conventions

This section provides detailed information about using graphic elements in documentation, the different types of graphic elements that are available, and specific advice on creating graphics.

When to Use Graphics in Documentation

As with many other items in documentation, using graphics is a judgment call, decided by the writer. The question you should always ask yourself is, "How can I best communicate with the reader?"

When Should I Use Graphics?

Every graphic that you include in user documentation should have purpose and should be directly related to the text surrounding it. Use graphics to:

  • Explain a complex concept more clearly or succinctly.
  • Identify a poorly labeled field or a difficult-to-locate item in an application.
  • Identify a symbol or icon used in an application.
  • Provide visual clues in documentation, such as an important note.

Graphics are useful in several areas including:

  • Online Help: Our users are now accessing our products (and online help) on tablets and phones, which only allow one window (application OR help) to display at a time. Visual references to the application are more helpful when online help is used in this way.
  • Word/PDF Output: Screenshots are needed for documents, as our customers can use these graphics in a variety of situations, including times when they're not near a computer running our software.
  • Complex/Conceptual Uses: Screenshots are always appropriate for complex screenshots that require call-outs to identify the parts of the screen you are talking about. Flowcharts are often very useful in explaining concepts and processes that are hard to explain in words.

When Should I Avoid Using Graphics?

Do not include a graphic in technical documentation for purely decorative purposes. Graphics without purpose draw the reader's attention away from more important content on the page and break up the text flow.

Do not include graphics that do not add value to the text. For example, do not include a graphic of an application page just to include it. If you do not reference the graphic in the surrounding text, you probably do not need it.

Graphics complicate the maintenance cycle. If a product changes the user interface, a column arrangement, or even just a field name, you have to update any graphics that reference that page. Adding unnecessary graphics increases your maintenance workload over time.

Types of Graphics

Graphics play an important role in training guides by helping users understand concepts, identify interface elements, and follow procedures more easily. Depending on the purpose of the content, writers may use basic graphics, inline graphics, callout graphics, or conceptual graphics to provide visual support and enhance the learning experience. Understanding the appropriate use of each graphic type keeps training guides clear and consistent.

Graphic Buttons and Icons

Products often use font-based graphics as buttons or icons, sometimes with accompanying text. Include these graphics in the text to help users identify buttons.

A button is an interactive object. An icon is a non-interactive object.

When to use

These graphics clarify processes or features of a product. Use the graphic the first time you mention the button or icon in the topic. Always place the graphic before the button name.

Maintaining the Buttons and Icons Library

The Documentation Team maintains button and icon graphics in a library. This library is separated by product, and each button or icon has a variable assigned to it for ease of use and maintenance.

When instructional writers use button and icon graphics, they must keep the following guidelines in mind:

  • Products are not universally up to standards. the Documentation Team can only provide SVGs of buttons and icons from the Font Awesome 4, Font Awesome 5, Font Awesome 6, Nova, or RealPage font libraries.

If a button or icon falls outside of these libraries, use a screenshot in your documentation, instead of a SVG.

  • All SVG buttons and icons are black. This is deliberate, as it makes the buttons and icons look like part of the text of your help.

If you have a button or icon that requires color, such as status icons that may indicate different values by color, you must use a screenshot of the button or icon in your documentation.

If you use any screenshots for buttons or icons, these screenshots should be no bigger than 18x18 pixels.

A basic graphic is a minimally styled screenshot that helps to clarify or identify aspects of the product. The graphic may be included in an instructional list, as part of an introductory topic, or used to illustrate the completion of a process.

Examples of minimal styling include cropping, removing bad data, or resizing.

Conceptual Graphics

Graphics can be worth a thousand words when aiding the reader with understanding complex concepts, processes, or workflows. In these cases, a graphic can provide a general overview of the concept, while the supporting text provides a greater understanding of each element of the image. These graphics are very rarely based on screenshots and are much more often illustrations created in Visio, Illustrator, Photoshop, or other graphic design programs. You can even create simple representational graphics in PowerPoint or SnagIt.

  • Process flowchart: Process flowcharts illustrate the stages of a process at a high level. For example, a graphic that shows how payments are batched and processed through the ACH system.
  • Workflow: Workflow graphics illustrate the steps of a task at a high level. For example, a graphic that provides an overview of how the HUD repayment plan process works.
  • Organizational: Organizational graphics are common in training materials and illustrate the major components of a section to the reader or learner. For example, a graphic that explains the directional flow between SDE, Payments, and Accounting processes.
When to use

Use conceptual graphics to help explain difficult concepts or complex processes that are difficult to explain succinctly using text alone.

When not to use

Don't use conceptual graphics to explain concepts or processes that are not complex. For example, if you draft a graphic that contains three or fewer separate components, a conceptual graphic may not be needed to explain the concept to the reader.

Logos

There are very few instances where our documentation uses logos. We reduced logo use to only a few key locations in the documentation. In almost every instance, the RealPage logo is preferred over specific product logos. This provides a unified look and also covers instances where a product doesn't have a usable logo. Today, logos are used on the cover page, on the web help header, and in quick step guides.

Primary reasons we don't often use product logos inside of documentation:

  • Some products don't have a logo.
  • Product logos can quickly become outdated, especially when a product name changes.
  • Logos are important to us, but not our readers. Logos are essentially invisible.

Logos aren't needed in most cases, as they only rarely add value to a user guide. In all instances, you should refer to current guidance from the Marketing and Legal teams to ensure that you're following accepted standards and within legal guidelines for logos.
